# 可解释智能定价规则引擎

## 解决的问题

原预订流程始终采用客房表中的固定单价，无法根据未来入住率、周末需求、提前预订和连住天数辅助经营决策；价格也只由前端计算，缺少服务端可信校验和事后审计依据。

当前实现提供“报价预览 → 下单重算 → 快照留痕”的完整链路。它是可解释的业务规则引擎，不宣称使用机器学习。

## V1 规则

基础价优先使用有效促销价，否则使用客房挂牌价。各规则采用加法叠加，并按间夜保留两位小数；总调整率预留 `-30%` 至 `+80%` 的保护区间。

| 维度 | 条件 | 调整 |
| --- | --- | ---: |
| 周末需求 | 周五或周六 | +15% |
| 预测入住率 | 低于 30% | -8% |
| 预测入住率 | 60%–79.99% | +10% |
| 预测入住率 | 不低于 80% | +20% |
| 提前预订 | 提前 14–20 天 | -5% |
| 提前预订 | 提前至少 21 天 | -8% |
| 临近入住 | 不足 3 天 | +10% |
| 连住优惠 | 3–4 晚 | -5% |
| 连住优惠 | 至少 5 晚 | -8% |

预测入住率按指定日期计算：有效订单占用的去重房间数 ÷ 非维护状态房间数。有效订单状态包括待确认、已确认和已入住。

## 一致性与可审计性

1. 用户选择日期后调用 `POST /api/pricing/quote` 获取逐日可解释报价。
2. 报价接口返回策略版本、基础价、动态均价、总价、每日预测入住率和命中规则。
3. 创建订单时，服务端在客房行锁和日期冲突检查之后重新报价，不信任客户端提交的 `price` 与 `totalAmount`。
4. 订单保存 `base_price`、`pricing_strategy_version` 和完整 `pricing_snapshot`，后续能解释成交价来自哪一版规则。
5. 报价与下单之间若库存发生变化，以事务内重新计算的成交价为准。

## 真实回归样例

回归日期：2026-08-30；客房：无障碍客房（基础价 289 元）；入住：2026-10-02 至 2026-10-05。

- 命中规则：周末需求、低入住率促销、提前 21 天预订、连住 3 晚优惠。
- 周五、周六间夜价：`289 × (1 + 15% - 8% - 8% - 5%) = 271.66` 元。
- 周日间夜价：`289 × (1 - 8% - 8% - 5%) = 228.31` 元。
- 三晚合计 771.63 元，动态均价 257.21 元。
- 回归请求故意提交 0.01 元，数据库实际保存 771.63 元及 `SMART_PRICING_V1` 的三晚快照，证明客户端无法篡改成交价。

## 数据库迁移

执行升级：

```powershell
mysql -uroot -proot -D hotel_management -e "source database/migrations/V3__booking_pricing_snapshot.sql"
```

需要回滚时先确认不再需要历史定价快照，再执行：

```powershell
mysql -uroot -proot -D hotel_management -e "source database/migrations/U3__booking_pricing_snapshot_rollback.sql"
```

## 当前边界

- V1 依据本系统订单预测入住率，尚未接入节假日、当地活动、竞品价格、渠道成本和收益管理人工审批。
- 规则阈值目前由代码版本管理，适合展示规则模式和服务端可信定价；下一步可改为配置表，并增加生效时间、优先级、灰度发布和审批记录。
- 当前目标是透明、可测试、可审计的经营决策辅助，不应在简历中描述为 AI/机器学习模型。
